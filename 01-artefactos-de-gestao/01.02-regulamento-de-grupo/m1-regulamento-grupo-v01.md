## 1. Instruções de utilização

Este documento é a base para cada grupo preparar o seu próprio regulamento interno. O grupo deve ler integralmente o modelo, substituir todos os campos de preenchimento obrigatório, decidir se pretende utilizar os conteúdos opcionais e confirmar que o resultado final é compatível com os documentos oficiais da unidade curricular.

Ao longo do documento são usados três tipos de conteúdo:

| Identificação | Significado | Tratamento obrigatório |
|---|---|---|
| **FIXO — NÃO ALTERAR** | Texto que assegura a articulação do regulamento interno com as regras da unidade curricular. | Deve permanecer no documento sem alterações. |
| **OBRIGATÓRIO — PREENCHER** | Decisão que todos os grupos têm de tomar e registar. | Todos os campos assinalados com `[PREENCHER: ...]` devem ser substituídos por conteúdo concreto. O texto que enquadra os campos deve ser conservado, admitindo-se apenas os ajustamentos gramaticais estritamente necessários para integrar as respostas. |
| **OPCIONAL — PREENCHER OU REMOVER** | Matéria que o grupo pode regular se considerar útil. | O bloco deve ser preenchido ou integralmente removido; não deve permanecer vazio. |

Os rótulos **FIXO — NÃO ALTERAR** devem permanecer na versão final, permitindo identificar as cláusulas que não podem ser modificadas. Os rótulos de preenchimento e as instruções entre parênteses retos devem desaparecer quando forem substituídos pelo conteúdo definitivo.

Na versão preparada pelo grupo, o título principal deve ser alterado para **Regulamento Interno do Grupo — [designação do grupo]**. A versão do regulamento deve ser indicada na secção 2 e refletida no nome do ficheiro segundo as regras de nomenclatura aplicáveis.

O grupo pode acrescentar regras próprias, desde que as identifique como conteúdo interno, não contrarie os documentos oficiais da unidade curricular e não altere matérias reservadas ao docente.

## 4. Comunicação interna e externa

### 4.1. Canais de comunicação



O canal principal para a comunicação corrente do grupo é o "Microsoft Teams" que inclui ainda o "Sharepoint" para acesso partilhado de informação. Este canal será utilizado para mensagens quotidianas, coordenação do trabalho e partilha de informação que não exija uma comunicação formal diferente.

O canal alternativo, a utilizar quando o canal principal estiver indisponível ou quando exista uma situação urgente, é "WhatsApp".

### 4.2. Prazo interno de resposta



Durante o período de funcionamento normal do grupo, cada elemento deve responder ou confirmar a leitura de uma mensagem que exija atuação no prazo máximo de 24 horas úteis. Uma confirmação de leitura não significa necessariamente que o trabalho pedido esteja concluído; significa que o aluno tomou conhecimento da mensagem e indicará, quando necessário, quando poderá responder de forma completa.

O grupo considera urgente uma mensagem relativa a impedimentos técnicos e atrasos de submissão de entregáveis. Nessas situações, será utilizado o canal secundário de comunicação, "WhatsApp", onde será descrito o problema existente e se necessário referenciar membros específicos.

### 4.3. Registo das decisões

> **FIXO — NÃO ALTERAR**

Uma mensagem informal não substitui uma decisão que, nos termos dos documentos oficiais, deva ser tomada numa reunião formal ou registada numa ata. Quando uma conversa informal revelar a necessidade de uma decisão formal, o grupo deve encaminhar a matéria para o procedimento aplicável.

### 10.2. Modelo de branches



O grupo utilizará as seguintes branches permanentes: **main e develop**.

As branches temporárias seguirão o padrão **<tipo>/i<numero_issue>-<descricao_curta>** (ex.: feature/i001-autenticacao-jwt, fix/i012-ecra-login-mobile). A convenção deve permitir relacionar a branch com a Issue correspondente.


### 10.3. Commits



As mensagens de commit seguirão a convenção **Conventional Commits no formato <tipo>(<escopo>): <descrição_curta> [I<numero_issue>]**. Cada commit deve ser suficientemente delimitado para permitir compreender a alteração e, quando aplicável, deve identificar a Issue através de 
**feat(backend): implementar endpoint de autenticacao JWT [I001]
fix(mobile): corrigir layout da lista de consultas no Android [I012]
docs(requisitos): atualizar matriz de rastreabilidade de requisitos [I005]**.


### 10.4. Merge Requests e integração

> **FIXO — NÃO ALTERAR**

As responsabilidades, a independência dos papéis e a sequência de revisão, auditoria, autorização e integração obedecem aos documentos oficiais da unidade curricular. Nenhuma regra interna, permissão técnica ou configuração da plataforma substitui essas obrigações.



Cada Merge Request deve usar **o modelo padrão do GitHub Pull Request com descrição das alterações, ID da Issue associada e checklist de verificação (compilação sem erros, testes a passar localmente e código formatado)**. A estratégia técnica de integração é **squash and merge**. Antes da integração, serão verificados **a conclusão com sucesso dos quality gates, a autorização do auditor e a posterior aceitação ou integração pelo revisor designado**.

As branches protegidas são **main e develop**. As permissões e regras de proteção aplicadas são **bloqueio de push direto, obrigatoriedade de Pull Request para integração, aprovação mínima de 1 Revisor e passagem com sucesso nas verificações automáticas de CI/CD**.

### 10.5. Releases, hotfixes e conflitos



As versões do software serão identificadas através de **Semantic Versioning no formato v<major>.<minor>.<patch>**. O procedimento para uma correção urgente é **criação de uma branch temporária no padrão hotfix/i<numero_issue>-<descricao> a partir da branch main, aplicação e teste da correção, revisão prioritária por 2 elementos e merge urgente para a main e develop com incrementação da versão do patch**. Os conflitos de integração serão resolvidos por **o autor da Pull Request em conjunto com o Revisor designado, realizando a resolução manual do conflito no ambiente local do autor antes da tentativa final de integração**, preservando a revisão e a rastreabilidade exigidas.

## 16. Divergências e resolução de conflitos

### 16.1. Princípio geral

> **FIXO — NÃO ALTERAR**

Uma divergência deve ser tratada com respeito, com base nas regras aplicáveis e nas evidências disponíveis. Nenhum aluno pode utilizar funções de administração, liderança ou acesso técnico para impor uma decisão, eliminar histórico, retirar acesso injustificadamente ou impedir os restantes elementos de apresentar a sua posição.

### 16.2. Procedimento interno



O grupo adotará o seguinte procedimento antes de solicitar uma decisão externa, quando a natureza e urgência da situação o permitam:

1. o problema é descrito em **documento escrito privado ou mensagem no canal de coordenação do grupo**, acompanhado dos factos, regras e evidências relevantes;
2. os alunos diretamente envolvidos procuram uma solução no prazo de **24 horas**;
3. se não existir acordo, **o Líder do grupo** conduz uma tentativa de mediação no prazo de **24 horas**;
4. quando seja necessária uma decisão formal, a matéria é encaminhada para **reunião formal extraordinária do grupo**;
5. se o impasse continuar, o pedido ao docente é preparado por **o Líder ou, na sua impossibilidade, por 2 elementos do grupo**, assegurando que todos os elementos recebem a comunicação exigida.

Os prazos internos anteriores não podem fazer ultrapassar um prazo oficial nem atrasar uma comunicação urgente ao docente.

### 16.3. Comportamento nas discussões



Durante uma divergência, os elementos comprometem-se a **manter tom estritamente profissional, focar a discussão em evidências objetivas e factos técnicos, escutar ativamente todas as partes e respeitar os momentos de fala**. Não são admitidos ataques pessoais, intimidação, ocultação de informação, alteração de evidências ou retaliação por uma posição expressa de boa-fé.
